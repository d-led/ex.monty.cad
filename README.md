# ex_monty_cad

The framework learns an object by sensing it, and its pretrained memories come from
episodes. A CAD part has already been explored: its surface is exact, and the
recognition names every face, so a node's label is a fact rather than a
conclusion. This package is the join between the two — the part on one side,
the framework's own percept and its library format on the other.

The API by module — and the same content as [`llms.txt`](https://d-led.github.io/ex.monty.cad/llms.txt)
for a model with no browser — is generated by `mix docs` and published at
[d-led.github.io/ex.monty.cad](https://d-led.github.io/ex.monty.cad/) from `main`;
the released version is on [HexDocs](https://hexdocs.pm/ex_monty_cad).

```elixir
{:ok, part} = Quiddity.open("bracket.step")

# What a sensor module perceives here:
{:ok, camera} = Quiddity.Camera.patch([15.0, 0.0, 13.0], [0.0, 0.0, 1.0], distance: 5.0)
{:ok, frame} = Quiddity.frame(part, camera)
{:ok, message} = MontyCad.Percept.message(frame)

MontyCad.Percept.node_features(message)
#=> %{"pose_vectors" => [...], "principal_curvatures_log" => [0.0, 0.0], ...}

# The library a run loads:
{:ok, written} = MontyCad.Training.write(part, "bracket", "bracket.jsonl.gz", spacing: 2.0)
written.nodes
#=> 186
```

The percept is the framework's own code — `Monty.Frameworks.Models.SensorModules.ObservationProcessor`
over the frame — not a re-implementation, so a node trained from a part is the
percept a run would have made. `docs/bridge.md` says exactly what is faithful and
what is not.

## The three modules

| Module              | What it answers                                                                                                                                   |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MontyCad.Percept`  | A `Quiddity.Frame` as the observation a sensor module reads: `semantic_3d`, shaded `rgba`, `cam_to_world`, and the message Monty builds from them |
| `MontyCad.Training` | Visits over the part's surface, one percept each, with exact labels from the recognition                                                          |
| `MontyCad.Library`  | The file: gzipped JSON lines, one record per node, in the shape `GraphLM` reads                                                                   |

`MontyCad.Percept.node_features/1` merges the morphological and non-morphological
features the way `GraphLM.select_features_to_use/2` does — those are the columns
a record stores.

## From a shell

    mix monty_cad.train bracket.step --object bracket --out bracket.jsonl.gz

`--spacing` sets the millimetres between visits, `--limit` the most visits to
make. The answer names the file, the nodes, the features held, and how many nodes
each feature family contributed.

## A policy that walks a part

`MontyCad.Policy.FeatureWalk` is a motor policy that already decides something,
and the shortest way to see what a policy with the geometry can do: each step it
ray-casts from the sensor onto the exact surface, keeps the sensor a patch's
standoff off it, and walks one step towards the next feature the part's
recognition named — a hole's centre, a boss's top — until the ray lands on that
feature's own faces. It never reads the observation or the percept, which is the
point: a policy with the part knows where the next feature _is_.

```elixir
{:ok, part} = Quiddity.open("bracket.step")
{:ok, recognition} = Quiddity.features(part)
policy = MontyCad.Policy.FeatureWalk.new(part: part, recognition: recognition)

MontyCad.Policy.FeatureWalk.describe()
#=> %{"name" => "monty_cad.feature_walk", "kind" => :motor_policy,
#     "placement" => :owner_only, "needs" => [:quiddity, :monty], ...}
```

It is `:owner_only` because it holds a B-rep, and it asks for `:quiddity` and
`:monty` because it calls both — the `needs` a cluster checks against what the
node carries before it routes a call there.

## Writing a plugin: the generators

A run is assembled from modules — a motor policy that decides where to sense
next, a sensor transform that turns one observation into a percept. Each has a
contract in the framework's own behaviour, and a cluster that will call it wants a
description of it first. Two generators write both halves, so what you fill in is
the decision and not the wiring:

    mix monty_cad.gen.policy follow_chamfers
    mix monty_cad.gen.transform surface_smoother

Each writes a module and a test:

|            | `follow_chamfers`                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------ |
| the module | `lib/<your_app>/plugins/follow_chamfers.ex` — `Monty.Frameworks.Models.MotorPolicies.MotorPolicy`'s callbacks and `describe/0` |
| the test   | `test/<your_app>/plugins/follow_chamfers_test.exs` — it describes itself, it is a motor policy, it forgets between episodes    |

`call/6` and `call/3` raise with a sentence saying what to answer, on purpose: a
generated body that looks like an answer is a decision nobody made. The policy is
`:owner_only` (it reads a B-rep, and a B-rep handle cannot leave its node); change
that in `describe/0` if yours does not, and the test will follow the description.

The description is `MontyPlugin`'s contract — kinds, placements, needs — and
`MontyPlugin.conforms?/1` says what is wrong with one that a cluster cannot
use. A cluster asks over the protocol; this package asks the same question in a
test.

## Checking them

    mix monty_cad.plugin.check

Every module of your application that describes itself as a plugin, checked
against the contract: the description conforms, and the callbacks its kind
requires are exported. Run it in CI — the compiler refuses a missing callback, but
a description is a map, and a map drifts in silence until a run asks for the
plugin and fails somewhere else.

## Install

```elixir
def deps do
  [
    {:ex_monty_cad, "~> 0.6.1"}
  ]
end
```

This package is Elixir only, but `ex_quiddity` builds a Rust engine when it is
compiled, so **building wants a Rust toolchain and running wants none**.

## Releasing

Nothing is published from a branch: `ci` proves a commit, a tag says it is a
version. The version lives in `VERSION` and is written into `mix.exs` (and the
dependency line above) by the script that moves it:

```bash
elixir scripts/release.exs bump patch     # 0.2.0 -> 0.2.1, in every file
git add -A && git commit -m "release: 0.2.1" && git push
./scripts/tag_and_push_version.sh          # refuses a dirty tree or red CI
```

The tag is what `.github/workflows/release.yml` publishes from, and that job needs
the `HEX_API_KEY` secret on this repository.

## Limits, said out loud

- A CAD frame is perfect: no sensor noise, no occlusion from a real probe. A
  library trained from one is a library trained from a drawing; `docs/bridge.md`
  says what that costs.
- A library holds the part, densely and evenly. It does not hold an exploration
  policy — that is what a training episode is, and this package does not replace
  one.
- The labels are exact because the recognition named the faces, not because
  anything was inferred. Where quiddity could not prove a feature,
  `Quiddity.Recognition.unexplained_faces/1` is where that is visible.
- A node whose patch saw too little surface is skipped and counted, not stored:
  an empty percept is not a node.
